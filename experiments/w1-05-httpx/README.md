# w1-05 · httpx 接真实 API

> W1 第四天。前三天学的并发、限流、重试、类型校验，今天要用**真实 HTTP 请求**把它们串起来。

---

## 这个实验想搞清楚什么

1. 一次大模型 API 调用，在 **HTTP 层面**到底长什么样？
2. 网络请求会以哪些方式失败？**每一种该不该重试？**
3. 流式（SSE）和非流式到底差在哪？为什么它让超时语义变合理了？
4. **为什么「HTTP 200」不等于「结果能用」？**

---

## 四个脚本

| 文件 | 主题 | 一句话结论 |
|---|---|---|
| `01_raw_call.py` | 原始调用 + 连接池 | 大模型 API 就是「约定好字段名的 JSON 交换」，没有魔法 |
| `02_timeout_errors.py` | 超时 + 错误分类 + 静默失败 | 「该不该重试」问的是**重试能不能改变结果** |

**建议按顺序跑**，后面的实验依赖前面建立的概念。

## 实测数据（2026-10-11，DeepSeek `deepseek-flash`）

### ① 连接池：为什么 `AsyncClient` 必须复用

用 `GET /models` 测（该端点不消耗 token），各跑 3 次：

| 方式 | 第 1 次 | 第 2 次 | 第 3 次 | 后续均值 |
|---|---|---|---|---|
| A 每次新建 client | 566.8 ms | 581.0 ms | 664.5 ms | **622.7 ms** |
| B 复用一个 client | 191.3 ms | 106.4 ms | 79.5 ms | **92.9 ms** |

**B 比 A 快 6.7 倍。** 因为 A 每次都在重走 DNS → TCP 握手 → TLS 握手。

### ② 错误分类：同一条请求，6 种失败

| 场景 | 抛出的异常 | 可重试？ | 耗时 |
|---|---|---|---|
| 忘了带 API Key | `HTTPStatusError` 401 | ❌ | 0.3 s |
| 模型名完全瞎写 | `HTTPStatusError` 400 | ❌ | 0.3 s |
| 域名不存在（关代理） | `ConnectError`（DNS 失败） | ✅ | **0.2 s** |
| 目标不可路由（TEST-NET-1） | `ConnectTimeout` | ✅ | **3.2 s** |
| 读取超时（`read=0.05`） | `ReadTimeout` | ⚠️ 谨慎 | 0.05 s |
| 域名不存在（走代理） | `ProxyError` 502 | ❌ | 0.6 s |

> **排障技巧**：同为「连不上」，DNS 失败 **0.2 秒**就报错，`ConnectTimeout` 硬等满 **3 秒**。
> 看耗时就能区分是「名字解析不了」还是「包发出去了没人应」，不用猜。

### ③ 流式 vs 非流式

| | 总耗时 | 首个输出（含思考） | 首个**正文** | 字数 |
|---|---|---|---|---|
| 非流式 | 2.92 s | 2.92 s | 2.92 s | 170 |
| 流式 | 2.41 s | **0.96 s** | **1.98 s** | 219 |

**流式的总耗时不一定更短**（有时反而略长，因为每个包都要单独编解码）。
它的唯一卖点是：用户**更早看到有动静**。

> ⚠️ 反直觉的一点：思考模式下前 1 秒都在生成 `reasoning_content`。
> 如果你只把 `content` 显示给用户，流式的优势会被思考过程吃掉一半。

### ④ 思考模式开关：同一个问题，成本差 8.6 倍

| 模式 | 平均耗时 | 输出 token | 其中思考 | 正文为空 | 合计成本 |
|---|---|---|---|---|---|
| 思考开启（默认） | 2.82 s | 1076 | **1041（97%）** | **1/3 次** | ¥0.004835 |
| 思考关闭 | **1.28 s** | **103** | 0 | **0/3 次** | **¥0.000565** |

最戏剧化的是第三题（较难·设计）：

| 模式 | 输出 token | 正文 | 成本 |
|---|---|---|---|
| 思考开启 | **900（全部是思考）** | **0 字（空的）** | ¥0.003945 |
| 思考关闭 | 77（0 思考） | **102 字** | ¥0.000377 |

**开着思考不仅贵 10.5 倍，而且一个字答案都没给出来。**

### ⑤ 并发闸门：同样是 10 个任务

| 并发上限 | 总耗时 | 成功率 |
|---|---|---|
| 2 | 2.54 s | 10/10 |
| 10 | **0.82 s** | 10/10 |

快 3.1 倍，和 Day 2 推的公式 `T ≈ ⌈N / C⌉ × t` 吻合。

## 关键发现（这几条值得背下来）

### 1. 过时的模型名会被**静默替换**

```
请求 model = "deepseek-v4-flash"
响应 model = "deepseek-flash"     ← HTTP 200，不报错
```

官方说明：legacy names 仍被接受，但对应模型已退役，请求由 V4.1-Flash 服务。

**危险在哪**：如果你遍历 `["deepseek-v4-flash", "deepseek-flash"]` 做对比评测，
会得出「两个模型表现完全一样」的结论 —— 而实际上它们**就是同一个模型**，
整个实验从根上无效。

**对策**：启动时调一次 `GET /models` 核对（免费），对不上就报错。

### 2. 「HTTP 200」和「结果可用」是两件事

三种静默失败：

| 形态 | 怎么发现 |
|---|---|
| `finish_reason == "length"` | 检查这个字段，不能只看状态码 |
| `content` 是空字符串 | 检查正文是否为空 |
| 格式对但字段名不对 | Pydantic 模型校验 |

**对策**：把静默失败**转成异常**。宁可炸在离现场最近的地方。

### 3. 思考模式下 `temperature` 是**无效的**

官方原话：「设置这些参数不会报错，但也不会生效。」
受影响参数：`temperature` / `top_p` / `presence_penalty` / `frequency_penalty`。

**为什么阴险**：不报错。你写 `temperature=0` 以为能固定输出，
结果每次还是不一样，会误以为是「模型不稳定」。

### 4. 坏消息：你本地见到的异常类型，换个环境就变了

同一个 URL（`.invalid` 域名），只因为环境里多了两个环境变量：

```
无代理 → ConnectError（DNS 查不到）
有代理 → ProxyError（代理替你去查，然后 502）
```

所以 `except` 必须留一个**宽基类兜底**（`httpx.RequestError`），
不能只列你本地见过的那几个具体类型。

### 5. `POST /chat/completions` **不幂等**

重试 = 可能重复计费。三种情况（响应丢了 / 还在生成 / 根本没收到）**你分不出来**。

对策见 `02_timeout_errors.py` 第三幕：幂等键、流式续传、给单次成本设天花板。

## 踩的坑

### 坑 1：把 `deepseek-v4-flash` 当成了正确模型名

写实验时从旧笔记里抄的模型名。用 `GET /models` 一查才发现服务端列的是
`deepseek-flash`。更坑的是**用错名字不报错**，服务端会静默替换。

> **教训**：模型名不要凭记忆写。启动时跟服务端核对一次，成本为零。

### 坑 2：httpx 0.28 的 `Timeout()` 不能再无参调用

```python
httpx.Timeout()        # 0.27 及以前合法
# 0.28：ValueError: httpx.Timeout must either include a default,
#       or set all four parameters explicitly.
httpx.Timeout(5.0)     # ✅ 正确
```

### 坑 3：以为「关掉思考就一定能拿到答案」

第一版 demo 里写：同样的 `max_tokens=32`，开着思考会截断，关掉就能成功。
**实测打脸** —— 32 个 token 对那个问题本来就不够，关掉思考也照样截断。

改成固定问题的对照后才成立：`max_tokens=64` + 短问题，
开思考 → 截断，关思考 → 输出 10 token 成功。

> **教训**：对照实验要**一次只改一个变量**。
> 我第一版同时改了「思考开关」和「答案所需长度」两个变量，结论就是错的。

### 坑 4：本机有代理，导致「连不上」变成另一种错误

`.invalid` 域名本来应该触发 DNS 失败（`ConnectError`），
实测拿到的是代理返回的 `ProxyError: 502 Bad Gateway`。

绕开办法是 `httpx.AsyncClient(trust_env=False)` —— 不去读 `HTTP_PROXY` / `HTTPS_PROXY`。

> 顺带发现：**DeepSeek 关掉代理直连更快**（0.3 s vs 走代理的 0.6 s）。
> 所以不要把 `base_url` 指向国内 API 的请求塞进代理。

## 这些知识用在了哪

全部进了 `src/llmkit/`：

| 实验里的发现 | 在 `llmkit` 里的落地 |
|---|---|
| 连接池必须复用 | `LLMClient` 只建一个 `httpx.AsyncClient`，用 `async with` 管生命周期 |
| 超时四参数 | `DEFAULT_TIMEOUT = Timeout(180, connect=10)` |
| 错误分类 | `client.is_retryable()` —— 可重试/不可重试分两张表 |
| 抖动退避 | `_post_with_retry()`，`random.uniform(0, base * 2**attempt)` |
| 429 的 `Retry-After` | 优先读响应头，比自己猜准 |
| 静默失败 | `is_truncated` 检查 + `TruncatedResponseError` |
| 模型名核对 | `verify_models()` |
| 思考默认关 | `disable_thinking=True` |
| 成本统计 | `ClientStats` + `price_of()` |

端到端演示跑 `python scripts/llmkit_demo.py`。
