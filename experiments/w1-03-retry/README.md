# W1-03：失败重试 —— 指数退避 + 抖动

> 本文件已填好全部答案。

## 想搞清楚什么

网络请求失败，多数不是「坏了」，是「这一下没成」：

- 429 Too Many Requests —— 你发太快了
- 502 / 503 / 504 —— 网关或服务端打了个盹
- 连接超时、连接被重置

这类失败**过一会儿再试往往就成功**，所以工程代码里必须有重试。

但重试做错了，比不重试还糟：

> 100 个客户端全都在 0.5 秒后一起重试。
> 服务刚缓过来，又被这 100 个请求同时打垮 —— 如此循环。
> 这叫**惊群效应（thundering herd）**。

本实验对比四种策略，重点看第四个：把重试时刻「摊开」。

## 怎么跑

**PyCharm**：目录树里右键 `retry_backoff.py` → `Run 'retry_backoff'`

**命令行**：

```bash
cd experiments/w1-03-retry
python retry_backoff.py          # 默认 20 个客户端
python retry_backoff.py 2000     # 也可以自己指定规模（看「规模的影响」一节）
```

只用到标准库，全程不到 4 秒。

> 想在 PyCharm 里换规模：`Run → Edit Configurations...` → 在 `Parameters` 里填 `2000`。

## 四个策略

| 策略 | 等待时间 | 说明 |
| --- | --- | --- |
| A 不重试 | —— | 对照组 |
| B 固定延迟 | 0.2s / 0.2s / 0.2s | 最常见的新手写法 |
| C 指数退避 | 0.2s / 0.4s / 0.8s | 教科书答案 |
| D 指数退避 + 抖动 | `[0, 2^n × 0.2]` 随机 | **生产推荐** |

## 实测结果（N = 20）

20 个客户端、单次失败率 60%、最多重试 3 次。

**四个策略面对的是完全相同的失败序列**（固定了随机种子），所以数据可以直接横向比。

| 策略 | 成功率 | 总耗时 | 最密集窗口（0.05s 内同时重试） |
| --- | --- | --- | --- |
| A 不重试 | 45% | 0.06 秒 | 0 |
| B 固定延迟 | 90% | 0.86 秒 | **11** ← 惊群 |
| C 指数退避 | 90% | 1.66 秒 | **11** ← 惊群 |
| D 指数退避 + 抖动 | 90% | 1.29 秒 | **7** |

B 版的重试时刻表 —— 一眼就看出问题：

```
0.264 0.264 0.264 0.264 0.264 0.264 0.264 0.264 0.264 0.264 ...
```

11 个客户端挤在同一个毫秒。

## 三个关键发现

### ① 重试确实能救命

45% → 90%。而且这还是在单次失败率高达 60% 的条件下。

### ② 光有「指数退避」不够 —— 这是本实验最重要的结论

C 和 B 的最密集窗口**数值完全一样，都是 11**。

为什么？因为指数退避只改变了「等多久」，没有改变「谁和谁一起等」。所有客户端的等待时间**依然是同步的**：大家都在 0.2 秒后、都在 0.6 秒后、都在 1.4 秒后 —— 只是间隔被拉长了，撞车照旧。

**而且 C 付出了代价**：总耗时 0.86 → 1.66 秒，**几乎翻倍，却什么也没换到**。

### ③ 抖动才是解决惊群的那一半

D 把每一轮的等待时间在 `[0, base]` 之间随机打散，最密集窗口从 11 降到 7。

额外收益：**平均等待更少**。`uniform(0, base)` 的均值只有 `base / 2`，所以 N 小时 D 的总耗时明显低于 C。

不过这个优势会随 N 收窄 —— 因为总耗时由**最慢的那个客户端**决定，N 越大越容易抽到接近上限的样本。所以「总耗时」这类取 max 的指标，单次测量波动很大，只看趋势，别看绝对值。

**正确的写法是：`random.uniform(0, base * 2 ** attempt)` —— 退避和抖动缺一不可。**

（这个做法叫 **full jitter**，出自 AWS 的《Exponential Backoff and Jitter》。）

## 规模的影响：20 个客户端够不够？

实验做完才想到的问题：**样本量会不会影响结论？**

我把客户端数从 20 扫到 2000（只用命令行参数，代码没动）：

```bash
python retry_backoff.py 2000
```

| N | B / C 最密集 | D 最密集 | B / C 占比 | D 占比 |
| --- | --- | --- | --- | --- |
| 20 | 11 | 7 | 55% | 35% |
| 100 | 61 | 28 | 61% | 28% |
| 500 | 295 | 109 | 59% | 22% |
| 2000 | 1236 | 443 | 62% | 22% |

### 结论一：占比稳定 → N=20 得出的结论方向是对的

B / C 始终占客户端的 55% ~ 62%，D 始终占 22% ~ 35%。**这个比例不随 N 变化**，所以「指数退避无效、抖动有效」这个判断在大规模下依然成立。

用 20 个客户端看趋势，够用。

### 结论二：但绝对规模是线性爆炸的 —— 这才是重点

盯着 D 那一列看：**7 → 28 → 109 → 443**。

抖动把系数从 0.6 压到了 0.22，但**没有改变「线性增长」这件事**。算一下就明白了：

```
第一轮要重试的客户端 ≈ N × 失败率 = 0.6N
抖动把它们摊在 [0, 0.2] 秒内
密度 = 0.6N / 0.2 = 3N 个 / 秒
0.05 秒的窗口内 ≈ 3N × 0.05 = 0.15N
```

**这个 `0.15N` 就是地板。** 只要抖动的摊开范围（0.2 秒）不变，N 翻十倍，窗口内的并发就翻十倍。

N = 2000 时，**仍有 443 个请求在同一瞬间砸向服务端** —— 这足以打垮任何服务。

### 结论三：所以抖动不是银弹，必须叠加并发上限

| 手段 | 管什么 | 能解决线性爆炸吗 |
| --- | --- | --- |
| 指数退避 | 等多久 | ❌ |
| 抖动 | 谁和谁一起等 | ❌ 只能把系数降下来 |
| **Semaphore** | **同时在飞的请求数** | ✅ |

`Semaphore(5)` 意味着**永远最多只有 5 个请求在飞**。第 6 个只能在门口排队 —— 排队的人再多，也不会同时到达服务端。

**这就是 Day 2 两道菜的完整拼图：**

```
Semaphore  ←  管「同时在飞多少个」（空间维度）
Jitter     ←  管「什么时候重新加入队列」（时间维度）
```

少一个都不行。

## 哪些错误该重试，哪些不该

这是重试逻辑里最容易做错的地方 —— **不是所有失败都值得重试**。

| ✅ 该重试（瞬时故障） | ❌ 不该重试（重试一万次也一样） |
| --- | --- |
| 429 Too Many Requests | 400 Bad Request（请求格式错） |
| 500 / 502 / 503 / 504 | 401 Unauthorized（认证失败） |
| 408 Request Timeout | 403 Forbidden（无权限） |
| 连接超时 / 连接被重置 | 404 Not Found |
| DNS 临时解析失败 | 422 Unprocessable Entity（参数校验失败） |

**判断标准**：重试一次**有可能变好**的 → 重试；问题出在**你自己的请求**上的 → 立刻失败，别浪费配额。

把这套逻辑实现错，会出现最尴尬的情况：API Key 填错了，程序勤勤恳恳重试 3 次、苦等 1.4 秒，然后告诉你「还是 401」。

## 三个必须设的上限

重试逻辑不设边界，就是给自己埋雷：

1. **最大重试次数** —— 通常 3~5 次。无限重试 = 死循环
2. **单次调用超时** —— 否则一个卡住的连接能吃掉所有时间预算
3. **总耗时预算（deadline）** —— 整条重试链路不能超过比如 30 秒

## 还有一个坑：Retry-After

429 和 503 的响应里经常带一个响应头：

```
Retry-After: 5
```

意思是「5 秒后再来」。**这时候要听服务端的**，而不是用你自己算出来的退避时间 —— 对方比你更清楚它什么时候能接客。

## 踩的坑

> **坑一：样本量太小，真实差异「看起来不成立」。**
> 第一次跑的时候参数没调好（失败率 0.5、20 个客户端），只产生了 8 次重试。
> B / C / D 的最密集窗口区分不出来（6 / 6 / 4）。把失败率提到 0.6 后变成 19 次重试，差异立刻显现（11 / 11 / 7）。
>
> **教训**：做对比实验时先怀疑样本量，再怀疑结论。
>
> **坑二：不同指标对样本量的敏感度完全不一样。**
> 「占比」类指标在 N=20 时已经稳定，「绝对值」类指标则线性于 N。
> 判断样本够不够，要先问一句：**我要测的这个量，它本身依赖 N 吗？**
